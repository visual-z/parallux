# 流向图动画 60 帧流畅、满载不超预算、没有流量时不耗 CPU

## 问题

2026-11-19 作者要求：动画不能有性能问题，要流畅；可以重构，不要在局部最优上打补丁。`fix-overview-design-parity` 的实现是一个 30 帧的 `TimelineView` 包一个 `Canvas`，每帧把流带、节点、粒子全部重画。实测（仓库外的渲染脚本，Release 构建，804×330 pt，满载约 900 个粒子，`top -l 2`）：

| 做法 | App CPU | 备注 |
|---|---|---|
| 现状 30 帧 | 3.3–3.8% | 粒子每帧走约 7 pt（速度约 200 pt/s），看得出一格一格跳 |
| 现状改 60 帧 | 5.6–5.7% | 超出 PLAN §5 的 5% |
| 现状跟显示器刷新率（160 Hz 屏实得 117 帧） | 8.5–9.2% | |
| 60 帧，空画布 | 2.1–2.2% | `TimelineView` + `Canvas` 自身的底噪 |
| 60 帧，不画流带 | 4.0–4.1% | 流带约占 1 个百分点 |
| 60 帧，不画粒子 | 3.9–4.1% | 粒子约占 1 个百分点 |
| 60 帧，几乎没有流量 | 4.1–4.4% | 没东西可动也照样每帧重画 |

查过的做法（2026-11-19 检索）：

- SwiftUI Lab《Advanced SwiftUI Animations – Part 5: Canvas》（https://swiftui-lab.com/swiftui-animations-part5/）：给 `.animation` 日程设 `minimumInterval`，并把静态内容与动画内容拆成两个 Canvas，作者的例子从 30% 降到 6%。
- DEV《Two SwiftUI animation loops that burned CPU on my Mac with nothing on screen》（https://dev.to/appsbymo/two-swiftui-animation-loops-that-burned-cpu-on-my-mac-with-nothing-on-screen-4d6j）：弹出面板里的循环动画关掉后必须停；作者把一个循环挪到 Core Animation 后 App 进程从 32% 降到 0.3%。
- twostraws/Vortex（约 1.6k star，MIT，https://github.com/twostraws/Vortex）：SwiftUI 粒子库，只参考做法，不引入依赖（它是通用粒子系统，不认识「沿流带走」）。

Core Animation 方案做了原型对拍（仓库外，66 条 `CAReplicatorLayer` 轨道、995 个点）：App 进程 0%，但 WindowServer 在三轮交替对比里平均多出约 20 个百分点（同机 Canvas 方案的 WindowServer 增量在噪声内）——开销只是从 App 挪到了 WindowServer，而且粒子的密度、带内横向位置都要改成离散轨道。否决。

所以保留 Canvas，改结构：流带与节点一层，只在流量变化后的缓动期间重画；粒子一层，60 帧，只在有流带时存在。缓动从「每帧向目标靠近一个比例」改成定长曲线：前者永远到不了目标，流带层就永远停不下来，而且快慢跟帧率有关。

## 完成定义（动工前冻结；实现中不得放宽）

- **D1** 缓动是时间的函数、与帧率无关：任意分步方式走完同样的时间，结果相同；过程中每个值都在起点与终点之间（不越界）；走满 `FlowEase.duration` 后恰好等于终点并报告已到位；中途换目标时从当前值接着走（不跳变）；节点个数变了就直接取新值；步长为 0、负数、非有限数、远超时长都不出错。
  - 检：property `flowEaseIsFrameRateIndependentAndLandsExactly`
- **D2** 满载（约 900 个粒子）60 帧时 App 进程 CPU ≤ 5%；没有流量、窗口不可见、开了「减弱动态效果」三种情况下为 0。
  - 检：measure 仓库外渲染脚本，Release 构建，`top -l 2` 各取两次，数字记在证据里
- **D5** 交给 GPU 的三角网格：每股画出来的流带一片，面积恰好等于厚度 × 两段的宽度；顶点都在绘图范围内；每条线路、每个出口与中柱各有一个节点，至少 6 pt 高、与柱同宽；不承载流量的线路有虚线、承载的没有；顶点总数不超过 `FlowMesh.maxVertices`；没有流量时没有流带。
  - 检：property `flowMeshCoversEachBandExactly`
- **D3** gate 全绿；测试计数只因本卡新增的测试而增加，既有测试没有被弱化。
  - 检：cmd `keel assert-guard --card docs/tasks/perf-flow-animation.md`
- **D4** 作者看真实窗口：粒子流动顺滑、不一格一格跳；流量变化时流带平滑过渡；断流几秒后画面静止。
  - 检：author 打开主窗口概览与菜单栏面板各看 10 秒

### 最终结果（2026-11-19，作者定「继续压到预算内」之后）

对「流量每秒变化」的上一版做了 `sample`（8 秒）：粒子一侧已经到底（主线程 1.3%，Metal 的几个队列约 1.4%）；超预算的全在 SwiftUI——每次流量变化后的 0.4 秒里，流带画布连同标签逐帧重排（`NSHostingView.layout` 1.4%）、重建显示列表并整层提交，合计约 2.8%。于是把逐帧变化的东西全部交给 GPU：流带、虚线、节点由 `FlowMesh` 生成三角形，与粒子在同一层里画（4 倍多重采样）；SwiftUI 只剩标签，每秒随新样本更新一次，不再跟着缓动逐帧移动。

上屏测量（同一脚本，Release，804×330 pt，10 秒窗口，`ps` 的 CPU 时间；两轮）：

| 情况 | 第一轮 | 第二轮 |
|---|---|---|
| 稳态满载（约 900 个粒子） | 4.5% / 4.6% | 4.2% |
| 流量每秒变化 | 4.9% / 5.0% | 4.5% |
| 闲时（48 Kbps） | 4.1% | — |
| 没有流量（不跑显示链接，画面是静态的一帧） | 0% | 0% |
| 加上三张卡片、流量每秒变化 | 5.8% | — |

**上面的数字只适用于 Release 构建、且只有流向图本身。** 复查时补测（同一脚本，10 秒窗口）：

| 构建 | 范围 | 稳态 | 流量每秒变化 |
|---|---|---|---|
| Release | 只有流向图 | 3.4% | 3.8% |
| Release | 流向图 + 三张卡片（整页概览） | 3.5% | 4.9% |
| Release | 面板的迷你流向图 | 4.2% | — |

| **Debug** | 流向图 + 三张卡片 | 8.0% | 8.0–8.7% |
| **Debug** | 面板的迷你流向图 | 4.5% | — |

- **`scripts/build-signed.sh` 装的是 Debug 构建**，所以作者在活动监视器里看到的会是 Debug 那几行（约 6–9%），不是 5% 以内。PLAN §5 没写预算按哪种构建计；发布构建（`release.sh`）是 Release。Debug 下多出来的时间在 Swift 自己的代码里（未优化的粒子步进与逐帧回调），`sample` 显示 `FlowParticles.step` 2.2%、其中逐粒子的线性查找 1.5%；把查找换成查表、缓存稳态布局之后 Debug 的数字没有明显变化（6.2% / 7.3%），所以瓶颈不在那两处，我没有找到。
- 「Release、整页、流量变化」第二次测到 0.9%，那一次屏幕中途锁定（`CGSSessionScreenIsLocked = 1`），作废；表里的 4.9% 是锁屏前的一次。
- 小窗口并不便宜：面板的迷你流向图（316×64 pt）与概览的大图几乎一样（4.2% 对 3.4–4.6%）。开销主要是每秒 60 次呈现，不随面积变。

- D2：两种有流量的情况都不超过 5%，但余量很小（最高一次正好 5.0%）；没有流量为 0。窗口不可见时不跑显示链接也不重画（结构保证；本版没有单独测）。**减弱动态效果时不是严格的 0**：没有粒子、没有缓动，但每来一个新样本要重画一帧（每秒一帧），没有测量。
- 稳态比「只有粒子在 GPU 上」的上一版（3.3–3.5%）高了约 1 个百分点。关掉多重采样对比过，只差 0.1–0.2（4.0% / 4.4% 对 4.2% / 4.5%），不是它造成的；两版不是在同一时刻测的，机器负载不同，所以这 1 个百分点里有多少是真实的我不知道。`sample` 里稳态合计 3.6%（主线程 1.7%，其余是 Metal 与 Core Animation 的队列），这是 60 帧呈现本身的开销。
- 上屏截图看过三张：满载（浅色）、流量变化、没有流量（节点与虚线，静态路径）。离屏把渲染器画进纹理读回，看过浅色满载、深色闲时（虚线、淡色节点、加亮粒子）。
- 没有验证的：真实 App 里的样子；缓动本身看起来是否顺滑（截图看不出）；标签不再跟着缓动走之后的观感。

### 真实 App（2026-11-19，作者要求合入并安装后；Debug 签名构建 20261119120557，概览可见，1 条线路，约 1 Mbps，164 条连接）

- CPU（`ps` 的 CPU 时间，两个 10 秒窗口）：**10.9% / 10.6%**。高于脚本里的任何一个数字，D9 在真实 App 里没有达标。
- `sample` 8 秒，按采样占比估算（不是精确值）：约一半的时间在 `NSHostingView.minSize()` → 整个窗口的 `sizeThatFits`（经概览的 `ScrollView` 量到三张卡片，其中 `ViewThatFits` 在量尺寸时还在反复新建 `NSSegmentedControl`）；这是每秒数据刷新触发的整窗布局，不是 60 帧的那一层。流向图逐帧的工作（显示链接回调加 Metal 的队列）约占七分之一，折合约 1.5% 的一个核。
- 所以真实 App 超预算的原因不在动画，而在概览页每秒一次（可能不止一次：状态、连接、线路统计各自发布，`HeldFlowDiagram` 的计时循环每秒也改一次状态）的 SwiftUI 整窗重排，Debug 构建下尤其贵。脚本没有复现它：脚本里没有真实的窗口结构、连接列表和各路数据源。这部分没有修，也不知道改动前是多少（没有留旧版本的数字）。
- 真实窗口截图看过一张（深色，概览）：流向图、粒子、等高卡片、「命中最多」、工具栏的聚合方式都在。两处与设计稿不同：工具栏里电源按钮在聚合方式左边（设计稿在右边）；图上线路写 1.1 Mbps、两个出口合计约 115 Kbps、流量卡片 171 Kbps——线路速率来自网口计数（`feat-link-view`），出口来自连接，口径不同。

### 实现过程中的测量（仓库外渲染脚本，Release 构建，804×330 pt，约 900 个粒子；本机 160 Hz 外接屏，负载均值约 7）

开卡时表里的数字是**离屏窗口**量的，离屏窗口不参与合成，数字偏低。上屏之后（`ps` 的 CPU 时间除以墙上时间）：

| 做法 | 稳态 | 流量每秒变化 | 说明 |
|---|---|---|---|
| 两个 Canvas（流带一层、粒子一层），60 帧 | 10.0% | 12.6% | 拆层本身不够：粒子 Canvas 每帧都要整层光栅化并提交 |
| 粒子改 Metal（MTKView），标签仍是带隐式动画的 SwiftUI 视图 | 4.6% | 12.8% | 标签的位置动画每次流量变化多花约 6 个百分点 |
| 同上，标签改成流带 Canvas 里的 symbol | 3.0–3.2% | 6.4–7.2% | |
| 同上，流带层缓动降到 30 帧（10 秒窗口，两次） | 4.2–4.3% | 7.7–7.8% | 与上一行在噪声内，缓动的开销不随帧数成比例 |
| 没有流量 | 0–0.1% | — | 粒子层不存在，流带层只画一次 |

对「流量每秒变化」那一档做了 `sample`（6 秒）：主线程 3.9%，其中 `Renderer.draw` 约 1.0%、`CA::Transaction::commit` 约 1.2%；**`CVDisplayLink` 线程 1.9%**——MTKView 的显示链接按屏幕刷新率（160 Hz）醒来，再丢掉多余的帧；Metal 提交队列约 0.9%。据此把 MTKView 换成 `CAMetalLayer` + `NSView.displayLink`（按要的 60 帧醒来）。

**最终方案的上屏数字（屏幕解锁后补测，2026-11-19，同一脚本、10 秒窗口）：** 稳态满载 3.3% / 3.5%；闲时（48 Kbps）3.7%；深色五出口 4.3%；流量每秒变化 6.0% / 7.3%；没有流量 0%；加上三张卡片、流量每秒变化 8.3%（卡片里的图表每秒重画，不属于流向图）。显示链接 10 秒触发 600 次（60 帧）；上屏截图里粒子在流带内。换显示链接对总数的改善在噪声内（上一变体 3.0–4.3% / 5.6–7.8%）。下面一段是锁屏期间写的，保留作过程记录：

**（锁屏期间）最终方案没有上屏数字。** 换完显示链接后屏幕已锁定、显示器休眠（`CGSSessionScreenIsLocked = 1`），窗口不可见，App 按设计停止动画，测到的 0% 不是性能数字；`screencapture` 也拿不到窗口。所以：

- 已验证（不需要屏幕）：渲染器画到离屏纹理、读回像素、叠到 SwiftUI 的流带图上看过——粒子落在流带里，颜色、浅色覆盖与深色加亮都对（设计稿数字 10771 个亮像素，五出口深色 7531，闲时 652）；流带、节点、标签（改成 Canvas symbol 后）离屏渲染正常；135 个 Swift 测试全绿。
- 未验证：`NSView.displayLink` 驱动的上屏呈现（显示链接是否按 60 帧触发、粒子是否出现在屏幕上）；最终方案的 CPU。上一个变体（MTKView，同一个渲染器）上屏时在画，有 `sample` 为证，但我没有留下它的截图。
- 未对拍的系统假设：`NSView.displayLink(target:selector:)` 在视图不可见时自动暂停（Apple 文档的说法）。即使不成立，窗口不可见时粒子层本来就会被移除（`WindowVisibility`）。
- D2 的结论（以补测为准）：稳态满载 3.3–3.5% 在预算内；没有流量 0%；流量每秒变化时 6.0–7.3%，**超出 5%，D2 未达标**。实际使用中流量基本每秒都在变，所以后一个数字更接近真实情况。窗口不可见与减弱动态效果两项为 0 是由结构保证的（粒子层不存在、流带层的时间线暂停），窗口不可见一项在锁屏时实测为 0。

## 交接

- 做了什么：流向图里逐帧变化的东西全部由 GPU 画（`FlowLayer`：流带、虚线、节点、粒子，60 帧，4 倍多重采样）；几何是 Kit 里的纯函数 `FlowMesh`，流带的网格只在布局变了才重建。SwiftUI 只画标签，每秒更新一次。显示链接只在有东西在动时运行（有流量，或正在缓动）；其余时候输入变了才画一帧，窗口不可见时什么都不做。缓动是定长曲线 `FlowEase`。没有 GPU 时退回一张静态的 Canvas。
